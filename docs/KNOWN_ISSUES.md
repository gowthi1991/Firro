# Known issues

Nothing here blocks review. Items are ordered by how much they matter before launch.

1. **Still open before this is finished (same list as the README's "Launch configuration" table):** (a) **legal review of the privacy notice** (retention period, processor list, grievance contact); the draft banner and draft wording were removed at the owner's request, but the text hasn't been reviewed. (b) Lead notification emails are skipped until `LEAD_NOTIFY_EMAIL` is set (`RESEND_API_KEY` is in Production only). (c) No social profiles in `SOCIAL`. Filled: the WhatsApp number, the contact email (`support@getfirro.com`), and lead storage on `/api/lead`.
2. **Two overlaps exist in the approved desktop design and were kept.** The hero prep-sheet card covers part of the "Carbs" orbit chip, and the nutrition "linked ingredients" card covers the Fibre "9g" value. Both are the same in the reference.
3. **Automated tests run in Chromium only**, which is what CI installs. The Safari/Firefox scroll-reveal fallback was checked by hand in Playwright's WebKit and Firefox builds (all 47 reveal elements show on scroll, no console errors). A real iPhone and a low-end Android haven't been tried.
4. **Lighthouse was run against `astro preview` on localhost** with simulated mobile throttling. Numbers on the production host and CDN will differ a little.
5. **Bricolage Grotesque has no italic**, so the italic accents are synthesised by the browser. This matches the reference.
6. **The mobile FAB (56px, bottom-right) floats over content as you scroll**, for example the last value in a card. It hides over the hero CTAs and the demo form. Everywhere else, the overlap is the usual trade-off for a floating button.
7. **`npm audit` reports 3 high-severity advisories** (`path-to-regexp` ReDoS, GHSA-9wv6-86v2-598j) through `@astrojs/vercel` → `@vercel/routing-utils`. That code runs at build time to generate routing config and never sees request input. The only offered fix downgrades the adapter three majors (`npm audit fix --force` → 8.0.4), which would break the build. Revisit when the adapter updates.
8. **Lead emails haven't been tested end to end.** Storage was verified against the real Neon database once, on a preview (see item 12). A Resend email hasn't gone out yet, because `LEAD_NOTIFY_EMAIL` isn't set (item 13).
9. **The rate limit isn't atomic.** It counts then inserts, so a burst of parallel requests for one number could store a 4th lead. That's fine for a demo form.
10. **A slow Resend adds up to 8s** before the visitor sees "Got it." (the email is awaited with a timeout, then logged if it fails).
11. **The Neon database is in `us-east-1` (N. Virginia), not Asia**, while the function runs in Mumbai (`bom1`). Every query crosses between the two, which makes a lead submission noticeably slower than it needs to be. Options: create the Neon project in an Asia region (for example Singapore) and move the data, or, until then, pin the function to `iad1` next to the database. Nothing was deleted or recreated.
12. **One test lead is still in the `leads` table** (id `2a663f1d-efff-4e82-989c-776052f74f88`, name "TEST - delete me", phone `+919000000001`). The Neon variables are sensitive and the Neon console needs a logged-in Vercel browser session, so it couldn't be deleted from here. Run in the Neon SQL editor: `DELETE FROM leads WHERE id = '2a663f1d-efff-4e82-989c-776052f74f88';`
13. **Lead notification emails are skipped** until `LEAD_NOTIFY_EMAIL` is set (logged as `[lead] RESEND_API_KEY or LEAD_NOTIFY_EMAIL not set`). `RESEND_API_KEY` exists in Production (and Development) but not Preview, so previews never email. `LEAD_FROM_EMAIL` uses `leads@getfirro.com`, which needs the domain verified in Resend.
